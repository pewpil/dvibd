# `mail` Project Context

This file contains context specific to the `mail` workspace (`gui`, and the planned `api`). Repository-wide standards and instructions live in the repository root `AGENTS.md`.

## Workspace Structure
- `mail/gui`: Mail client SPA built with Vite and Svelte 5. Client-side only: no server runtime, no SSR, no file-based routing.
- `mail/api`: planned backend API service, not yet scaffolded. Its port and the workspace pairing are already settled: gui on port `3006`, api on port `3007`. The GUI's dev proxy already reserves the pairing; when `mail/api` is scaffolded, register its specifics here. Runtime and framework decisions for it are deliberately deferred.

## GUI Specifics (`mail/gui`)
- **Framework & Runtime**: Svelte 5 with Vite. This app is **not SvelteKit**: there is no `@sveltejs/kit` dependency, no `src/routes/`, no `+page.svelte` files, no SSR, and no server endpoint. It is a client-side SPA in the same shape as `dvibd/gui`. Do not apply SvelteKit idioms (`load` functions, `$app/*` stores, form actions) here, and do not use Svelte 1/2-era or SvelteKit-only APIs in general.
- **Framework Idioms**: Svelte 5 runes rules live in the root `AGENTS.md` under "Svelte 5 Core (`mail`)".
- **Frameworks Not Used Here**: React, Next.js, SolidJS, SolidStart, Tailwind CSS, and svelte/store-based global state. There is no client router installed yet (`src/App.svelte` is the single page); the router choice is a pending decision for the ongoing GUI work. No generated Prisma client is consumed yet either; the generator decision lands alongside `mail/api`.
- **Styling mechanism**: CSS Modules, exactly like every other GUI in this repository. `*.module.css` files are imported as the `style` module in the `script lang="ts"` block of each `.svelte` component (`import style from "./styles/components/App.module.css"`), and elements reference them through it (`id={style.mailApp}` for a selector `main#mailApp`). Svelte's own component `<style>` blocks are not used in this app; all component styling lives in CSS Modules so the token system, scoping rules, and mirroring contract stay identical across the four GUIs. The `vite/client` types in `tsconfig.json`'s `types` array provide the `*.module.css` import typings; do not add custom ambient declarations for them.
- **Global CSS**: `src/styles/index.css` is the only plain stylesheet. It carries the `@fontsource-variable` imports (Rethink Sans Variable for body, Lexend Variable for headings, the same families as the other GUIs), the token blocks on `:root`, and the resets. Component styles never go there.
- **Design tokens**: `src/styles/index.css` currently seeds the shared "Indigo dusk" palette (`#f2f3f8` / `#0c0d14` light-dark backgrounds, `#6d5dfc` / `#8b7dff` accents) but in its legacy first-draft shape: `--primary` / `--primary-strong` / `--primary-soft` names, a `--surface-hover` token, a single dark block (media query only, no `[data-theme]` attribute path), dark `--surface` at `0.02`, and a distinct dark `--danger` (`#f87171`). When the GUI work continues, align it to the structure the other apps converged on (see `social/AGENTS.md` and `message/AGENTS.md`): rename to `--accent*` plus `--accent-ink`, use the neutral `--wash` for hovers, adopt the radius scale and the `--glass-shadow` / `--glass-inset` pair, keep the two dark paths in sync with identical tokens, and add the reduced-motion, reduced-transparency, `@supports not (backdrop-filter)`, and focus-ring fallbacks. The seeded palette hue values themselves are correct and stay.
- **Bootstrap**: `index.html` provides `div#app`, and `src/main.ts` mounts with `mount(App, { target })` from `"svelte"`, throwing when the mount target is missing. This is Svelte 5's bootstrap; do not use the Svelte 4 `new App({ target })` pattern.
- **Dev Server**: Port `3006`, defined in `vite.config.ts` `server.port`. That config proxies `/api` to `http://localhost:3007` and strips the `/api` prefix from the forwarded path, mirroring the `dvibd` workspace's dev pairing.
- **Build**: `vite build` produces a static `dist/` bundle; `npm run preview` serves it. Treat a local `dist/` as disposable scratch output.
- **Type Checking**: `npm run typecheck` runs `svelte-check --tsgo --tsconfig ./tsconfig.json`, and it must pass with zero warnings (Svelte's compiler emits a11y diagnostics through svelte-check; those warnings are part of the standard). This app cannot be checked with `npx tsc --noEmit`, which does not understand `.svelte` files. The package carries a deliberate dual TypeScript install: classic `typescript` pinned to `~6.0.3` solely because svelte-check's language tooling requires it, plus `@typescript/native` aliased from `npm:typescript@^7.0.2` (the repository-standard 7.x line), whose native compiler is invoked through the `--tsgo` flag. Keep both pins in sync with svelte-check releases; never resolve the compatibility pressure by downgrading the repository's 7.x track or bumping the classic pin past what svelte-check supports. `svelte.config.js` is minimal (`vitePreprocess()` only). `.svelte-check/` is generated scratch output (the checker's own tsconfig plus `.d.svelte.ts` declaration files) and is gitignored; commit nothing from it.
- **Deployment**: No `netlify.toml` exists yet. When the app is ready to deploy it follows the `dvibd/gui` shape confirmed for static SPA workspaces: its own `netlify.toml` beside `package.json` (base directory `mail/gui`), publish `dist`, the SPA redirect, and the ORM-generate-first build step only if the generated client ends up type-imported by the build.
- **File Mirroring**:
  - Every `.svelte` component has a parallel CSS Module under `src/styles/` with the same stem: root component `src/App.svelte` <-> `src/styles/components/App.module.css`; a new `src/components/ListRail.svelte` <-> `src/styles/components/ListRail.module.css`.
  - New components go under `src/components/` so their modules nest under `src/styles/components/` symmetrically. Do not move `src/App.svelte`; it is the mount root.
  - Element ids and classes are camelCase, taken from the component's CSS Module, and all selectors inside a module are fully nested `tag#id` containing `>` child chains, per the root GUI standards.
