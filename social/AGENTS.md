# `social` Project Context

This file contains context specific to the `social` application. Repository-wide standards and instructions live in the repository root `AGENTS.md`.

## Application Overview
- **Framework & Runtime**: SolidStart with Vite, running on Node (`npx tsc --noEmit` in `social/`).
- **Frameworks Not Used Here**: React, Next.js, Remix, and Tailwind CSS. This is SolidStart 2 on Nitro, not a React app, so the React skills (`vercel-react-best-practices`, `vercel-composition-patterns`) must not be applied here. Only `web-design-guidelines` carries usable guidance, and only its platform-level rules: ARIA, focus states, `prefers-reduced-motion`, `Intl.*`, semantic HTML, and touch targets. Its React-specific advice (controlled inputs via `value` plus `onChange`, `suppressHydrationWarning`, the nuqs state-sync suggestion) is wrong for SolidJS and should be ignored, and its Tailwind class syntax must be translated to CSS Modules. Local standards win on conflict: this repo requires ids over classes.
- **Contrast with `dvibd/gui`**: the two apps share `solid-js` and `@solidjs/router` and nothing else. This app is SolidStart with a Nitro server runtime; `dvibd/gui` is a plain client-side Vite SPA with no server runtime. See `dvibd/AGENTS.md`.
- **App icon**: `public/logo.svg` and `public/favicon.svg` carry the social product icon copied from `dvibd/gui/src/assets/components/dvibd/home/landing/product/social.svg` (the rose constellation). The user dislikes this artwork and it stands only as a placeholder until a preferred mark exists. `entry-server.tsx` links `/favicon.svg` (`stale favicon.ico` remains in `public/` as a legacy fallback), and the auth pages (`login.tsx`, `signup.tsx`) render `/logo.svg` inside `a#authBrand`.
- **File Mirroring**:
  - `src/routes/` and `src/styles/pages/` mirror each other (e.g. `src/routes/(home)/notifications.tsx` <-> `src/styles/pages/(home)/notifications.module.css`).
  - `src/components/` and `src/styles/components/` mirror each other (e.g. `src/components/(home)/FeedTabs.tsx` <-> `src/styles/components/(home)/FeedTabs.module.css`).

## Auth Architecture
- `social` is a self-contained backend ecosystem: it never proxies or relays to `api/`. It shares only `orm/` (Prisma client at `src/server/generated`, extension `mts`) and `db/` (Postgres).
- Auth HTTP routes live directly in `src/routes/(auth)/` with no `/api` prefix. Page files (`login.tsx`, `signup.tsx`) must stay client-safe: their verb handlers live in the route group `(auth)/(endpoints)/` (e.g. `(endpoints)/login.ts` exports `POST /login`; group parens are stripped from the URL).
- Never import server-only modules (`bcrypt`, `prisma`, `pg`, `h3`) into a file with a default page component; Vite dev loads the whole graph in the browser. Pure API route files (`session.ts`, `refresh.ts`, `logout.ts`, `me.ts`) have no component and are safe.
- Endpoints: `POST /login`, `POST /signup`, `GET /session`, `POST /refresh`, `POST /logout`, `GET /me`.
- Session strategy: refresh token (30 days) in httpOnly cookie `social.session`; access token (15 min) returned in the response body and kept in client memory. `GET /session` validates the cookie and issues a fresh access token; `POST /refresh` rotates the refresh token (old row deleted, new issued).
- `src/middleware.ts` verifies the cookie into `locals.loggedIn` and guards `/explore`, `/notifications`, `/bookmarks`, `/settings` (redirect `/login`) and redirects authed users off `/login` and `/signup`. Profile pages at `/@<username>` are public, so signed-out visitors can open any post author's profile.
- Password hashing uses native `bcrypt`. Server modules: `config.ts` (env resolution; the local scripts export `LOCAL_ENV=1`, so localhost runs lock to the dev defaults and ignore the environment, per the root `AGENTS.md` env policy), `db.ts` (Prisma singleton), `tokens.ts`, `session.ts`, `user.ts` (`SafeUser`, `USER_SELECT`); `auth.ts` is the `"use server"` facade (`fetchSession`) so SSR renders correct auth state.

## Data Architecture
`social` renders from Postgres, not from fixture modules. `orm/prisma/schema.prisma` is the single source of truth; there is no `src/data/social.ts` any more. The content models are `User`, `Post`, `PostMedia`, `Tag` / `PostTag`, `Like`, `Repost`, `Bookmark`, `Notification`, `NotificationPreference`, `Follow`, `Community` / `CommunityMember`, and `Happening`.

- **Server query modules** live in `src/server/` and wrap every read: `posts.ts` (`getFeed`, `getBookmarks`, `createPost`, shared `POST_INCLUDE` and `toPostCard`), `notifications.ts` (`getNotifications`, kind to phrase map), `profiles.ts` (`getProfilePage`), `discover.ts` (`getTrending`, `getTagNames`, `getSuggestedProfiles`, `getCommunities`, `getHappenings`), plus `postTags.ts` (`syncPostTags`) and `demoContent.ts`. Each exported query is defined with `query` from `@solidjs/router` and carries `"use server"` inside the callback. Write actions such as `createPost`, `setFollow` in `follows.ts`, `updateProfile`, and `updateNotificationPreferences` use `action` with explicit keys and the same directive. Do not put Prisma calls in client components or in any query callback or action without that directive.
- **Profiles.** Profile pages live at `/@<username>` through `src/routes/(home)/[handle]/index.tsx`. The route param is the whole `@username` segment because neither router supports a mixed literal-and-parameter segment; `route.matchFilters.handle` requires the leading `@`, and the page strips it before querying. `getProfilePage(handle)` resolves the username case-insensitively, returns `null` for an unknown handle (rendered as an inline missing-account state), and builds posts, replies, media, and likes from that author rather than the session user. Likes are public author activity. Post author names and handles link to their profile, and the AccountMenu is the only side nav entry point to the signed-in user's handle: the profile picture opens that menu and its "Go to profile" item navigates there. `ProfileCard` shows "Edit profile" only when the viewed author matches `useAuth().user()`, otherwise "Follow". `ProfileView.isFollowing` is computed per viewer in `getProfilePage` and stays `false` for signed-out viewers and for the profile owner. The Follow button on other profiles is a native form whose `action` is `setFollow` in `src/server/follows.ts` (action key `socialSetFollow`); it posts hidden `handle` and `intent` (`"follow"` or `"unfollow"`) fields, rejects signed-out viewers and self-follow with `{ ok: false, error }` instead of throwing, upserts or deletes the `Follow` row, and revalidates `socialProfilePage`, `socialFeed`, and `socialSuggestedProfiles` so the button label and counts settle after the action. `src/routes/[...404].tsx` catches every other path, so the old `/profile` test route is gone and unknown paths render a not-found page. It sits outside the `(home)` route group on purpose, so it does not inherit `src/routes/(home).tsx` and renders with no feed, no SideNav, and no Explore rail: a standalone `main#notFoundPage` state that only borrows the app tokens and type families.
- **Post permalinks.** A status post opens at `/@<username>/status/<post-id>`; `status` is the only routed type for now (the DTO still uses `stat` internally for a status post), and articles are not routed yet. `src/routes/(home)/[handle].tsx` is a pass-through layout that owns the `handle` filter; the profile page moved to `src/routes/(home)/[handle]/index.tsx` and the thread page is `src/routes/(home)/[handle]/[type]/[id].tsx`, whose `matchFilters.type` accepts only `status`. `getPostThread` (query key `socialPostThread`) returns the post plus its direct replies oldest first, and the thread page renders only those two, never the feed or profile header. `src/lib/postPath.ts` maps the internal `stat` type to the `status` URL segment and builds the canonical link. Every status `Post` card in feeds, profiles, bookmarks, and reply lists renders a transparent overlay link with author links, the more button, and the action buttons lifted above it while the card content stays `pointer-events: none`; article posts render no overlay, and the thread page passes `permalink={false}` to its current post so that post does not self-link. The post action bar shows Like, Views, Repost, Save, and Share; there is no Reply button, and the clickable card or the thread Composer is the reply path. `getPostThread` returns at most the newest 50 direct replies, oldest first, so the thread page renders that capped list. The thread page calls `recordView` with the route's canonical handle, type, and id once per mount and per parameter change, uses the returned count locally for the current post, and the action revalidates `socialFeed`, `socialProfilePage`, and `socialBookmarks` but not `socialPostThread`, so a reply draft survives. A signed-in viewer also gets a reply `Composer` (placeholder `"Reply"`) directly under the current post; it posts to `createReply` (action key `socialCreateReply`) with a hidden `parentId`, creates a `STAT` reply, increments the parent `replyCount`, syncs tags, and revalidates `socialFeed`, `socialProfilePage`, `socialBookmarks`, `socialTrending`, `socialTagNames`, and `socialHappenings`. Each Composer filters its submission by its own `parentId`, so only the submitting composer shows pending, error, or success, and a successful reply revalidates only that composer's exact `socialPostThread` key (`getPostThread.keyFor`) on the client instead of the whole key. Replies are status-only for now, so articles are not replyable through this route.
- **Reply trail.** The status page URL is always the post currently being viewed (`/@<handle>/status/<post-id>`). Clicking a reply navigates in-page to that reply's canonical URL and pushes the previous current post onto a compact ancestor trail above the current post: the trail shows the clicked ancestors oldest first with the immediate parent last, as avatar, name, handle, time, and one-line excerpt rows rather than full posts, and a decorative `aria-hidden` rail runs through the trail avatar centers to the current post's avatar. The trail is in-page state, not persisted: a hard refresh of any status URL shows that post as the current post with no trail, while browser back and forward follow history and select an existing trail entry instead of duplicating it. The header `BackButton` uses normal browser history: back returns to the previous clicked post and shrinks the trail, browser forward restores the child and grows it, and the oldest entry falls back to the normal history/home behavior. Each current-post change focuses the `h1` and scrolls to the top. Pointer and keyboard activation both drill in-page, while modified, middle, and new-tab clicks keep the canonical hrefs. The current post keeps its Composer, Replies list (at most 50 direct replies, oldest first), views, and the exact-key `socialPostThread` revalidation after a successful reply; articles are not replyable.
- **Settings.** `src/server/settings.ts` exports `getSettingsPage` (query key `socialSettingsPage`) for the signed-in user and the `updateProfile` action (action key `socialUpdateProfile`). The editable fields are display name, bio, website, avatar URL, and cover URL. The website accepts a bare domain and is normalized to a full `https://` URL before storage, while the two image fields accept a full http(s) URL or a root-relative path. Validation is zod-based against `MAX_DISPLAY_NAME_LENGTH`, `MAX_BIO_LENGTH`, `MAX_WEBSITE_LENGTH`, and `MAX_IMAGE_URL_LENGTH` from `src/types/social.ts`, failures return `{ ok: false, error }` instead of throwing, and a success revalidates `socialSettingsPage`, `socialProfilePage`, `socialFeed`, `socialBookmarks`, `socialNotifications`, and `socialSuggestedProfiles`. `/settings` is protected by `src/middleware.ts`; the page still renders its own sign-in prompt when the query resolves to `null`.
- **Notification preferences.** `getNotificationPreferences` (query key `socialNotificationPreferences`) and `updateNotificationPreferences` (action key `socialUpdateNotificationPreferences`) in `src/server/settings.ts` back the five toggles on `/settings`. Reads go through `readNotificationPreferences` in `src/server/notificationPreferences.ts`, which returns all five categories as `true` when the user has no `NotificationPreference` row, so the form defaults to everything enabled. The action upserts that row, treating a checkbox value of `"on"` as `true` and a missing field as `false`, and revalidates `socialNotificationPreferences` plus `socialNotifications`. `getNotifications` in `src/server/notifications.ts` maps the enabled preferences to `NotificationKind`s and filters the query by them, so a disabled category disappears from `/notifications`. Theme is deliberately not database-backed: it stays device-local in `ThemeToggle` through `localStorage` and a cookie.
- **Posting.** The home feed renders `Composer` above the posts for signed-in users only. It is a native `<form>` whose `action` is the `createPost` action in `src/server/posts.ts`. The action resolves the author from the session cookie, never from the client, trims and validates 1 to 256 characters with zod, creates a `STAT` post with `isFallback: false`, and runs `syncPostTags`. It returns `json({ ok: true }, { revalidate: [...] })`, which invalidates `socialFeed`, `socialProfilePage`, `socialTrending`, `socialTagNames`, and `socialHappenings`, so the new post appears at the top of the feed without a reload. `MAX_STAT_LENGTH` in `src/types/social.ts` is the shared limit for the form and the action. Failures return `{ ok: false, error }` instead of throwing, so the composer can show the message inline. The image button in the composer footer is deliberately disabled with `"Image attachments are coming soon"` until uploads exist; it is not wired to the post action.
- **DTOs are display-ready.** `src/types/social.ts` holds every wire shape (`PostCard`, `NotificationCard`, `ProfileView`, `TrendTopic`, and so on). Queries preformat relative timestamps (`"2h"`) and compact counts (`"12.4k posts"`) on the server with helpers in `src/server/format.ts`, so components keep their existing prop contracts and hydration cannot disagree with the server render.
- **Session helpers.** `session.ts` exports `readSessionUser()` (validated cookie to `SafeUser | null`, used by every query) and `readSession()` (adds an access token, used by `GET /session`). `USER_SELECT` / `SafeUser` in `user.ts` include the profile fields (`bio`, `website`, `avatarUrl`, `coverUrl`, `isFallback`). Client identity comes from `useAuth()` in `src/contexts/AuthContext.tsx`, which exposes `loggedIn()` and `user()`.
- **Hashtags drive discovery.** `syncPostTags` parses `#tag` tokens out of post text and materializes `PostTag` rows. Trending and the explore chips read the live counts, so they no longer carry static lists.
- **Fallback provenance.** Rows that originate from the old fixture data carry `isFallback = true` on `User`, `Post`, `Community`, `Happening`, `Notification`, and `Bookmark`. Demo notifications are flagged and render a subtle "Demo" chip in `NotificationItem`. The 18 fixture people (including the `dvibd` handle) are seeded with `@dvibd.local` emails and unguessable bcrypt passwords; `sadanddan` is deliberately left unseeded so the real owner can claim it.
- **Display counters.** `Post` carries `replyCount`, `likeCount`, `repostCount`, and `saveCount`, initialized from the fixture numbers by the seed. `viewCount` defaults to 0 and is written only by `recordView`, and `PostCard.views` maps it. `Like`, `Repost`, and `Bookmark` rows are per-user state, not the source of those numbers; the like action updates both, and Repost and Bookmark writes must do the same when they land. `setLike` (action key `socialSetLike`) takes a positional `postId` and an `intent` of `like` or `unlike`, inserts one `Like` row if absent or deletes it and updates `Post.likeCount` in one transaction, idempotently, and revalidates `socialFeed`, `socialProfilePage`, `socialBookmarks`, and `socialPostThread`. `PostCard.liked` is viewer-specific from `likedPostIds`, so a signed-out click navigates to `/login`, and no like notifications are created yet. `recordView` (action key `socialViewPost`) validates the canonical handle, the `status` type, and the post id before incrementing a `STAT` post's view count, then returns the new value. Follower and following counts are derived from `Follow`, so following or unfollowing writes the `Follow` row and the counts are rederived on the next profile query rather than edited directly.
- **Seeding.** Run `cd social && npm run db:seed` (it exports `LOCAL_ENV=1`, so it targets the local `db/` Postgres and ignores ambient variables). `scripts/seed.mts` is a tiny Vite SSR runner for `scripts/seedData.mts`, because the repo relies on bundler-style extensionless imports. The seed is idempotent: it exits when any fallback user exists. It inserts the fixture people, the three fixture posts plus their media and hashtags, three communities with memberships, three happenings, and a small follow graph.
- **Demo content at signup.** `POST /signup` calls `generateDemoContent(userId)` after the account row exists, wrapped in try/catch so demo generation can never fail a signup. On a seeded database the new account receives the four former "Sad And Dan" posts (including the reply to Aria's seeded post), 18 notifications mirroring the old fixture list, and two bookmarks. Every generated row is flagged `isFallback = true`. If the seed has not run, demo generation is a no-op. Delete `where: { isFallback: true }` rows to purge demo content.
- **Counts on the wire.** `compactCount`, `relativeTime`, and the plural helpers run only inside server queries; keep them out of components.

## Deployment
`netlify.toml` sits beside `package.json`, so the Netlify base directory is `social`. It publishes `dist` and relies on `nitro/vite`: Nitro detects the Netlify build environment and writes the catch-all function to `.netlify/functions-internal/server/server.mjs` with `path: "/*"` and `preferStatic: true`, so `dist` assets win and everything else reaches the function. The build command runs `npm --prefix ../orm run generate` first, because `src/server/generated` is gitignored and missing from a fresh clone. Do not add `@netlify/vite-plugin`: that path expects a `dist/client` publish directory and would change what this config publishes. The build command also carries the masked-secret guard described in the root `AGENTS.md` deployment section: `--secret` values reach local CLI builds masked, so the command unsets `DATABASE_URL` and `DIRECT_URL`, and `prisma generate` falls back to the local URL in `orm/config.ts` because it does not connect. There is no `orm/.env` and no dotenv; the app runtime env still comes from Netlify/`process.env`, not from `orm/`, while deployed functions read the unmasked value from Netlify env at runtime.

## Header Surface
`header#feedHeader` uses the same background treatment as `message`'s column headers and this app's `AccountMenu`: `background: var(--surface-strong)` plus `-webkit-backdrop-filter` and `backdrop-filter` of `blur(var(--blur))`, declared in the base rule so the frost is always present rather than appearing only when pinned.

Two consequences to keep in mind before changing it:
- The `blur` is unconditional, so `.stuck` only flattens the top corner radius. Do not re-add a blur to `.stuck`; it would be a duplicate. `.stuck` remains the signal that the header has pinned.
- In the light theme `--surface-strong` is `rgba(255, 255, 255, 0.85)`, so the header reads as frosted glass in both themes; the frost is part of the design, not an accident to fix. Dark theme keeps it at `rgba(255, 255, 255, 0.1)`.
- `ExploreHeader` and `BookmarksHeader` are unaffected in structure: they are transparent section headings inside the glass `FeedHeader`, not separate surface panels.

## Design Tokens (2026-10 rework)
The app follows the "Indigo dusk" token system set in `src/app.css` (the app's original bluish palette, restored 2026-10-20; names and structure unchanged). Key facts for future edits:
- **Accent, not primary.** The old `--primary` / `--primary-strong` / `--primary-soft` tokens were renamed to `--accent` / `--accent-strong` / `--accent-soft`. The accent is violet-blue (`#6d5dfc` light, `#8b7dff` dark) and is reserved for state: active tabs, selected filters, links, the theme-toggle hover, danger-adjacent emphasis. Generic hover states use `--wash` (a neutral ink wash), never `--accent-soft`.
- **`--accent-ink`** is the text/icon color to use on accent fills (`#ffffff` in both themes; `#8b7dff` on `#ffffff` matches the pre-rework look). Never hardcode `#fff` on top of an accent background.
- **Semantic tokens** `--like` (#f43f5e) and `--repost` (#22c55e) exist for post action states; `--danger` (#dc2626) for errors. All three keep the previous palette's literals, identical in both themes. Recolor them in `app.css` only, never in component modules.
- **Glass chrome vs paper content.** Glass (fill + blur + edge highlight via `box-shadow: var(--glass-shadow), var(--glass-inset)`) belongs only on chrome surfaces: `SideNav`, `FeedHeader`, `ThemeToggle`, `AccountMenu`, the explore rail Sections/Cards, the auth card, the settings profile, notification, and account panels, and the profile header stack (`img#cover` + `ProfileCard` + standalone `ProfileTabs`, which form one contiguous panel: cover owns the top border and top radius, the card owns the sides and the glass fill, the tabs own the bottom border and bottom radius). Posts, notification rows, and empty states are deliberately flat (`border: none`, transparent background) and separate with hairline borders (`:not(:first-child) { border-top: 0.0625rem solid var(--line) }`); `main#feed` carries no gap, the posts manage their own spacing.
- **Feed parity invariant (user decision, 2026-10-20):** the profile feed under the tabs is the same paper feed as `main#feed` on `/`: `div#profilePosts` is a chrome-less column and its `article#post` rows carry the identical flat styling from `Post.module.css`. Never wrap the profile posts inside the glass header stack; when `tabsStuck` fires, `ProfileCard`'s `complete` variant takes over the panel's bottom border and radius because the hidden tabs paint nothing.
- **Radius scale**, never one value everywhere: `--radius-panel` (1rem) for glass panels, `--radius-control` (0.625rem) for inputs and icon buttons, `999px` only for pills and avatars.
- **Fallbacks are token-level** in `app.css`: `@media (prefers-reduced-transparency: reduce)` swaps fills for opaque colors and zeroes `--blur`; `@supports not (backdrop-filter: blur(1px))` raises fill alphas; `:where(...):focus-visible` gives every control the accent ring; `@media (prefers-reduced-motion: reduce)` collapses every transition and resets `scroll-behavior` (all motion in the app is transition-based state response, no ambient keyframes).
- The light `data-theme="dark"` block and the `prefers-color-scheme` fallback block now carry identical values (the old `0.6` vs `0.02` `--surface` drift is gone); keep them in sync if either changes.
- **Units.** Typography, text-adjacent padding, control heights, and text-block gaps are `rem`. Borders and hairlines are `1px`, focus outlines and offsets are `2px`, the profile-tabs underline is `3px`, the media dots are `7px`/`5px`, and shadow offsets/blur plus `--blur`/`--blur-strong` (`14px`/`24px`, zeroed to `0px` under reduced transparency) are `px`. Layout widths, columns, and gutters stay relative (`--width: 76.5%`, `minmax(0, 40rem)`, `clamp()`). Media queries use `em`. The radius tokens (`--radius-panel`, `--radius-control`) and the `0.5rem`/`999px` radii deliberately stay in `rem`/`px` as design tokens; do not convert them per property. `div#app` uses `100dvh`; auth and 404 keep `100svh`.

## Theme Toggle
`src/components/ThemeToggle.tsx` renders on the home page and on both auth pages. It is an **icon** button, not a labelled pill: a moon glyph while the current theme is light, a sun glyph while it is dark, so the glyph always shows the theme it switches *to`. `aria-label` and `title` carry the same "Switch to X mode" wording and the glyphs are `aria-hidden="true"`, which is what keeps the accessible name unambiguous now that there is no visible text. The two paths follow the `iconProps` convention already established in `SideNav.tsx` (24px viewBox, `currentColor`, stroke 2, round caps and joins), and `message`'s `ThemeToggle.tsx` draws the identical geometry so the two apps stay visually consistent.

It takes `placement` (`"fixed"` or `"inline"`, default `"fixed"`) and `hideOnMobile`. The home page renders `<ThemeToggle hideOnMobile />`, so its fixed top-right control disappears below `60em`; the auth pages keep the default fixed control at every width. `SideNav` renders `<ThemeToggle placement="inline" />`, which is visible only below `60em` and sits in the mobile bottom bar next to the profile picture. Because two instances can be mounted at once, a toggle dispatches a `dvibd-theme-change` window event and every instance syncs to it, so resizing across the breakpoint never shows a stale glyph.

## Home Page Layout
The home page is composed of 3 vertical divisions inside `div#homeLayout`, laid out as a grid of fit-content, the feed, and the Explore rail:
- **Left division**: `nav#sideNav`, referred to as the side nav. A compact fit-content navigation sidebar containing only icons (plus the user's profile picture) that redirect the user when clicked.
- **Center division**: `main#feed`, referred to as the feed. Shows stat and article overviews:
  - Composer: signed-in users see `Composer` (`src/components/(home)/Composer.tsx`, mirrored at `src/styles/components/(home)/Composer.module.css`) between the sticky `FeedHeader` and the posts. It is flat paper like the posts, not a glass panel, and it is absent when signed out.
  - Profile: `/@<username>` renders the selected author's cover, profile card, tabs, and posts inside the same feed column. It is reachable from post author names and handles and from the profile picture's AccountMenu "Go to profile" item.
  - Settings: `/settings` renders the signed-in user's editable profile fields (display name, bio, website, avatar URL, cover URL) with live previews, the account-backed notification toggles, then read-only account details and sign out. It is reachable from the SideNav, the notifications header gear, and the "Edit profile" link on the user's own profile card.
  - Stat: a microblog of no more than 256 characters.
  - Article: longer writing with a title, headings, and text.
- **Right division**: `aside#explore`, referred to as Explore. Contains a search bar and the sections trending, users, community, and legal. The Users section is the "Who to follow" rail: each row is a native follow form that posts hidden `handle` and `intent=follow` fields to `setFollow`, and the action's `socialSuggestedProfiles` revalidation drops a followed account out of the list.

**Responsive behavior.** The CSS is mobile-first, and all breakpoints are in `em` so they follow the browser's text-size setting:
- Below `60em` (mobile, including 320, 390, and 768): one column. `nav#sideNav` becomes a fixed full-width bottom bar with a strong glass surface, safe-area padding, and no top/side radius; its link list is a row, tooltips are absent, and the theme control, message link, settings link, and profile menu stay available. The Explore aside is hidden. `main#feed` is full width inside `clamp(1rem, 3vw, 1.5rem)` gutters, and `div#homeLayout` reserves `calc(5.5rem + env(safe-area-inset-bottom))` so the bar never covers the last post. At 200% text the bar wraps to additional rows rather than clipping; the reserve was checked at 320px with a 200% root size.
- `60em` to `74.99em` (tablet): two columns, the vertical sticky `SideNav` rail plus the feed; the Explore aside stays hidden.
- `75em` and up (desktop): the original three columns, with the sticky Explore aside restored.

The `AccountMenu` opens upward from the bottom bar below `60em` and downward from the rail above it. Auth pages switch `#authInner` from 88% to 30% at `75em` (not the old 47.5rem), so the card is not crushed at 768.

## Left Nav Icon Set

Message links out to the standalone `message/` app, which owns all messaging functionality: it is a plain anchor rather than the router `A` so it leaves `social` in the same tab, and it resolves to `http://localhost:3005` in dev through `import.meta.env.DEV` and `https://message-dvibd.netlify.app/` in production. Its icon reuses the geometry and brand fills of `message/public/icon.svg`.

- Placeholder pages for the local icon routes live under `src/routes/(home)/`; Message is the external exception.
