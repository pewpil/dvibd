# `mail` Project Context

This file contains context specific to the `mail` workspace (`gui`, and the planned `api`). Repository-wide standards and instructions live in the repository root `AGENTS.md`.

## Workspace Structure
- `mail/gui`: Mail client SPA built with Vite and Svelte 5. Client-side only: no server runtime, no SSR, no file-based routing.
- `mail/api`: planned backend API service, not yet scaffolded. Its port and the workspace pairing are already settled: gui on port `3006`, api on port `3007`. The GUI's dev proxy already reserves the pairing; when `mail/api` is scaffolded, register its specifics here. Runtime and framework decisions for it are deliberately deferred.

## GUI Specifics (`mail/gui`)
- **Framework & Runtime**: Svelte 5 with Vite. This app is **not SvelteKit**: there is no `@sveltejs/kit` dependency, no `src/routes/`, no `+page.svelte` files, no SSR, and no server endpoint. It is a client-side SPA in the same shape as `dvibd/gui`. Do not apply SvelteKit idioms (`load` functions, `$app/*` stores, form actions) here, and do not use Svelte 1/2-era or SvelteKit-only APIs in general.
- **Framework Idioms**: Svelte 5 runes rules live in the root `AGENTS.md` under "Svelte 5 Core (`mail`)".
- **Frameworks Not Used Here**: React, Next.js, SolidJS, SolidStart, Tailwind CSS, and svelte/store-based global state. There is no client router installed yet (`src/App.svelte` is the single page); the router choice is a pending decision for the ongoing GUI work. No generated Prisma client is consumed yet either; the generator decision lands alongside `mail/api`.
- **Styling mechanism**: CSS Modules, exactly like every other GUI in this repository. `*.module.css` files are imported as the `style` module in the `script lang="ts"` block of each `.svelte` component (`import style from "./styles/components/App.module.css"`), and elements reference them through it (`id={style.mailApp}` for a selector `main#mailApp`). Svelte's own component `<style>` blocks are not used in this app; all component styling lives in CSS Modules so the token system, scoping rules, and mirroring contract stay identical across the four GUIs. The `vite/client` types in `tsconfig.json`'s `types` array provide the `*.module.css` import typings; do not add custom ambient declarations for them.
- **Global CSS**: `src/styles/index.css` is the only plain stylesheet. It carries the `@fontsource-variable` imports (Rethink Sans Variable for body, Lexend Variable for headings, the same families as the other GUIs), the token blocks on `:root`, and the resets. Component styles never go there.
- **Design tokens**: `src/styles/index.css` carries the shared "Indigo dusk" system in the aligned structure the other GUIs converged on (2026-10-21): `--accent` / `--accent-strong` / `--accent-soft` plus `--accent-ink` for text and icons on accent fills, the neutral `--wash` for generic hovers, the `--surface` / `--surface-strong` pair (dark `--surface` standardized at `rgba(255, 255, 255, 0.06)`), the radius scale (`--radius-panel` 1rem for glass chrome, `--radius-control` 0.625rem for controls, 999px only for pills), the `--glass-shadow` / `--glass-inset` pair, and the duration tokens. Tokens sit on `:root` with two dark paths that must stay byte-identical: `:root[data-theme="dark"]` (set by `ThemeToggle` through the localStorage key `mail.theme`) and the `prefers-color-scheme` media query gated with `:not([data-theme="light"])`. `--danger` is `#dc2626` in both themes; recolor semantic tokens in `index.css` only. Fallbacks are token-level: `prefers-reduced-motion`, `prefers-reduced-transparency` (opaque fills, zeroed blurs), `@supports not (backdrop-filter)` (raised fill alphas), the `:where(...):focus-visible` accent ring, `::selection`, and the thin scrollbar styling.
- **Bootstrap**: `index.html` provides `div#app`, and `src/main.ts` mounts with `mount(App, { target })` from `"svelte"`, throwing when the mount target is missing. This is Svelte 5's bootstrap; do not use the Svelte 4 `new App({ target })` pattern.
- **Dev Server**: Port `3006`, defined in `vite.config.ts` `server.port`. That config proxies `/api` to `http://localhost:3007` and strips the `/api` prefix from the forwarded path, mirroring the `dvibd` workspace's dev pairing.
- **Build**: `vite build` produces a static `dist/` bundle; `npm run preview` serves it. Treat a local `dist/` as disposable scratch output.
- **Type Checking**: `npm run typecheck` runs `svelte-check --tsgo --tsconfig ./tsconfig.json`, and it must pass with zero warnings (Svelte's compiler emits a11y diagnostics through svelte-check; those warnings are part of the standard). This app cannot be checked with `npx tsc --noEmit`, which does not understand `.svelte` files. The package carries a deliberate dual TypeScript install: classic `typescript` pinned to `~6.0.3` solely because svelte-check's language tooling requires it, plus `@typescript/native` aliased from `npm:typescript@^7.0.2` (the repository-standard 7.x line), whose native compiler is invoked through the `--tsgo` flag. Keep both pins in sync with svelte-check releases; never resolve the compatibility pressure by downgrading the repository's 7.x track or bumping the classic pin past what svelte-check supports. `svelte.config.js` is minimal (`vitePreprocess()` only). `.svelte-check/` is generated scratch output (the checker's own tsconfig plus `.d.svelte.ts` declaration files) and is gitignored; commit nothing from it.
- **Deployment**: No `netlify.toml` exists yet. When the app is ready to deploy it follows the `dvibd/gui` shape confirmed for static SPA workspaces: its own `netlify.toml` beside `package.json` (base directory `mail/gui`), publish `dist`, the SPA redirect, and the ORM-generate-first build step only if the generated client ends up type-imported by the build.
- **File Mirroring**:
  - Every `.svelte` component has a parallel CSS Module under `src/styles/` with the same stem: root component `src/App.svelte` <-> `src/styles/components/App.module.css`; a new `src/components/ListRail.svelte` <-> `src/styles/components/ListRail.module.css`.
  - New components go under `src/components/` so their modules nest under `src/styles/components/` symmetrically. Do not move `src/App.svelte`; it is the mount root.
  - Element ids and classes are camelCase, taken from the component's CSS Module, and all selectors inside a module are fully nested `tag#id` containing `>` child chains, per the root GUI standards.

## Mail App Layout Structure
`src/App.svelte` renders `main#mailApp` (from `src/styles/components/App.module.css`, referenced as `id={style.mailApp}`) as a two-track grid: the glass side panel plus one main column that swaps between the list, the read view, and compose. Layout constants live on `main#mailApp`: `--panel-width: 18.5%` (panel track), `--gap: 1.5rem`, and `--header-offset: 2.5vh` (consumed by both column spacers and by `nav#sidePanel`'s top and bottom margins, which lift the panel's top edge onto the column header's initial top line and keep its bottom edge off the viewport; the grid stretch then sizes the panel to the remaining track height, which is why it declares no `height`). The page is 76.5% of the viewport centered, matching the other GUIs. Below 47.5rem the panel drops out (`main#mailApp > nav { display: none }`) and the list header shows a folder `<select>` instead. There is no router yet: `App.svelte` is the single logged-in page, auth is deferred.

- **Column view state**: one string with three kinds of value, mirroring `message`'s single-source pattern: `"list"` (the folder or label list), `"compose"` (the full-column composer), or a thread id (the read view). "Which thing is showing" is one piece of state rather than a boolean plus an id.
- **SidePanel** renders `nav#sidePanel`, the ONE side panel (email metadata lives inline in the thread; there is deliberately no second info panel). Two content modes toggled by the profile chip (`panelMode`): `"navigation"` (profile chip, accent Compose button, folder list with counts, label filter rows) and `"account"` (identity block plus Settings, Terms, Privacy, Cookies, About, Help, Report a problem, and the danger-styled Log out; every row is inert until the backend lands).
- **EmailList** renders `section#emails`. Sticky glass `header#listHeader`: folder or label title, a search form scoped to the current bucket, and the All / Unread / Starred / Attachments tabs; the title row ends with the shared `ThemeToggle` (theme switching left the side panel, and the header placement keeps it reachable on mobile where the panel is hidden). Rows are one paper `ul#emailRows` separated by hairline dividers; each row is `button#rowButton` with the star as a separately positioned sibling `button#starButton` (interactive elements are never nested). Opening a thread marks it read and replaces the list column with the read view; there is no separate reading pane.
- **EmailView** renders `section#reading`. Sticky glass `header#readBar` carries back, star, reply, reply all, forward, then archive, junk, and delete, with the shared `ThemeToggle` last; the movers set the thread's folder and return to the list. Messages render chronologically as paper cards (outgoing tinted `--accent-soft`, drafts dashed with a Draft chip) with attachment chips, and the thread ends in a reply row that expands the inline composer.
- **Composer** is one shared component for `new` / `reply` / `replyAll` / `forward` modes. Recipients are comma-separated addresses parsed in the service; Send validates recipients and body; Save draft appears only in `new` mode and writes to Drafts; opening a Drafts row reopens the composer pre-filled through the `draft` prop, and sending that draft deletes the old draft thread. Quoted originals render as a muted blockquote, never as textarea text.
- **Labels** are filters, not a destination: a label id is a legal value of the same `activeFolder` state that folder ids use, and the list titles it with a colored dot via `style:--label-color`.

## Sticky Headers and Scroll Restore
Both column scrollers (`section#emails`, `section#reading`) satisfy the `sticky-scroll-headers` skill contract: the `&::before { height: var(--header-offset) }` spacer scrolls away, the header is `position: sticky; top: 0; z-index: 1` inside the scroller, and the stuck test compares rects (`header.top <= scroller.top + 1`). The Svelte implementation is `src/lib/stuckHeader.ts`, an attachment factory invoked as `{@attach stuckHeader(...)}` on the header: it owns the passive scroll listener, the resize listener, the initial on-mount test, and cleanup; the component keeps only a `stuck` boolean plus a setter callback. `.stuck` flattens only the top corner radius; the frost (`--surface-strong` + blur) is declared in the base rule and is never re-declared in `.stuck`.

List scroll position survives the list-to-read-to-list round trip through the plain module `src/lib/listScroll.ts`: the EmailList attachment snapshots `scrollTop` on every scroll, `resetScroll()` clears it on any folder, label, or send/draft navigation, and the attachment's restore parameter reapplies it on remount. The `{#key activeFolder}` wrapper in `App.svelte` remounts the list per folder so search and tab state reset with it, which is also what makes the restore correct.

## Data and Services
- `src/lib/mailService.svelte.ts` is a rune-store class instance (`export const mail`): `threads` is `$state` fixture data, and every mutation (`markRead`, `toggleStar`, `setFolder`, `sendNew`, `sendReply`, `saveDraft`, `deleteThread`) mutates it in place. Replace the internals with real API calls when `mail/api` lands; keep the method surface.
- `src/lib/fallback.ts` supplies the fixtures: `currentUser` (Alex Rivera), `fallbackContacts` (+ `labelList` for labels), and 11 threads covering inbox, sent, drafts, archive, junk, and trash with attachments (schema.prisma, a CI log, an invoice, an .ics, a palette png), quoted replies, outgoing messages, and one draft. Fixture copy follows the interface-writing standard: sentence case, no em dashes, no middots.
- `src/lib/types.ts` owns the model (`Contact`, `Label`, `Attachment`, `EmailMessage`, `Thread`, `FolderId`, `EmailTab`, `ComposeFields`) plus the `FOLDERS` / `TABS` constants and pure helpers (`threadUnread`, `threadHasAttachments`, `threadTouchesLabel`, `folderName`).
- `src/lib/theme.ts` (plain module) holds `THEME_KEY` (`mail.theme`), `readStoredTheme`, `applyTheme`, and `initialTheme`; `ThemeToggle` writes `data-theme` on the document root and persists through `applyTheme`.
- `src/lib/stuckHeader.ts` and `src/lib/listScroll.ts` are the sticky and scroll-restore plumbing described above.

## Relevant Skills
- Skills are installed under the repository root `.agents/skills/` and are discovered in every session; none are scoped to this directory. Eight apply here, plus one deferred design-time skill noted below.
- `svelte-core-bestpractices` and `svelte-code-writer` are the official pair from the Svelte team's `sveltejs/ai-tools`. The first is the runes and idiom guidance; the second wraps the official `@sveltejs/mcp` CLI for Svelte 5 documentation lookup plus the `svelte-autofixer` validator, which runs against `.svelte` and `.svelte.ts` files before finalizing. Their SvelteKit-specific portions do not apply because this app is a plain Vite SPA, and `svelte-code-writer`'s `svelte-file-editor` subagent does not exist in this repository, so run the skill inline.
- `security-and-hardening` and `security-review` are the repository's security pair for authoring and review. They matter here more than in the other GUIs: email bodies, attachment names, and recipient strings are untrusted input, and a mail client holds the most personal data in the repository. Neither skill documents Svelte or Vite, so apply their OWASP references as framework-general; the raw-HTML sink to flag in Svelte is `{@html}`, and ordinary interpolated values are escaped by default.
- `security-threat-model` from `openai/skills` is the design-time threat modeling skill reserved for the planned `mail/api`. It is deliberately not installed yet; add it with `npx --yes skills@1.5.14 add openai/skills --agent codex --skill security-threat-model -y` when the API design starts. It works from repository evidence, asks clarifying questions before writing, and produces a standalone `mail-threat-model.md`, so it belongs to that design step rather than to everyday GUI work.
- `sticky-scroll-headers` (hand-written, tracked in git) covers both column headers through `src/lib/stuckHeader.ts`; see the "Sticky Headers and Scroll Restore" section for the Svelte variant it now documents alongside the `message` and `social` implementations.
- `frontend-design` (any web UI) supplies aesthetic direction and copy guidance. `web-design-guidelines` (any web UI) supplies accessibility and platform rules; its Tailwind utility phrasing and React-specific sections are advisory only.
- `glassmorphism` is opt-in and fires only when glass or frosted surfaces are actually requested.
- The repository root `AGENTS.md` wins on every conflict; its skills section records precedence. In this app the live overrides are the styling mechanism above (CSS Modules over Svelte scoped `<style>`) and GUI standard 7's units policy (`rem` and `%` over `px`).
