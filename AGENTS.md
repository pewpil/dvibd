# `dvibd` Project Instructions

This file is the authoritative source of repository-wide standards that must be complied with. App-specific context lives in the workspace-scoped `AGENTS.md` files: `dvibd/AGENTS.md` (`dvibd` gui/api), `social/AGENTS.md` (`social`), `message/AGENTS.md` (`message`), `mail/AGENTS.md` (`mail`), `cv/AGENTS.md` (`cv`), `pics/AGENTS.md` (`pics`), `orm/AGENTS.md` (shared ORM), and `db/AGENTS.md` (database service). Contexts to remember live in the Workspace Memory section below.

## Repository Layout
- `dvibd/`: the main gui + api workspace (Node API, client-side Vite/SolidJS GUI).
- `social/`: a standalone SolidStart app (self-contained backend, Node runtime).
- `message/`: a standalone Next.js App Router app (self-contained backend, Node runtime).
- `mail/`: a standalone Vite + Svelte 5 app (client-side SPA; Node tooling). Its backend (`mail/api`, port 3007) is planned but not yet scaffolded. See `mail/AGENTS.md`.
- `cv/`: the personal CV site (React 19 + Vite, static SPA; Node tooling, port 3006). It carries its own git repository, and its content source is described in `cv/AGENTS.md`.
- `pics/`: the image platform (PHP 8.3+, Laravel 13, Livewire 4, Blade, Flux UI, Tailwind 4; local port 3008). It owns its Laravel migrations and its own `dvibd_pics` PostgreSQL database. See `pics/AGENTS.md`.
- `orm/`: shared Prisma schema, migrations, and generated clients (package `@dvibd/orm`). The Node apps are clients of this ORM; they do not define their own schema. `pics` is the deliberate exception: Laravel migrations own its schema.
- `db/`: local test Postgres via docker-compose (see `db/AGENTS.md`).
- `.opencode/`: OpenCode project configuration.
- `.agents/skills/`: agent skills. Most are third-party skills that are gitignored and fully regenerable; `skills-lock.json` at the repository root is the tracked source of truth. `pics` adds eight Laravel Boost generated skills to the same directory; they are regenerated by Boost, not by the lock. Hand-written skills such as `sticky-scroll-headers` are tracked in git instead. See ORM & DB Standards below.

## Cross-Cutting Coding Standards
1. Use double quotes (`"`) for any string literal in JS/TS code, never single quotes. PHP follows Laravel Pint and Laravel's quoting convention; see `pics/AGENTS.md`.
2. Write fully-typed TypeScript and TypeScriptXML code. No variable, parameter, or function may be declared without an explicit type (return types included).
3. Do not add code comments unless explicitly asked.
4. Refrain from using the em dash in any written output or content.
5. Never commit secrets or API keys. A secret that must live on disk belongs in a gitignored `*.key` file next to the configuration that references it, and is pulled in through `{file:*.key}` substitution. Never inline a key value in `opencode.json`.

## Runtime & Typecheck Standards
- Every JS/TS workspace runs on Node. `dvibd/api` is a Hono HTTP API on the Node server adapter; it has no Deno runtime, `deno.json`, or `deno.lock`, and its strict compiler flags live in `dvibd/api/tsconfig.json`. `pics` is the PHP workspace and runs on PHP 8.3+ with Composer.
- **Node Version Policy**: every Node workspace targets the latest Node.js **LTS** release, currently Node 24 ("Krypton"). Node 26 and other Current or EOL lines are out of policy. Each Node workspace declares `"engines": { "node": ">=24" }`, and `@types/node` is pinned to the matching `24.x` line so the types reflect the oldest supported runtime rather than whatever happens to be installed. Do not bump Node majors until a newer line reaches LTS; when one does, update `engines` and `@types/node` together across `dvibd/api`, `dvibd/gui`, `social`, `message`, `mail/gui`, `cv`, `orm`, and `pics` (asset tooling only).
- **TypeScript Version Policy**: TypeScript has no LTS concept, so every Node workspace tracks the latest release, currently `^7.0.2`. Keep it aligned across all of them. `mail/gui` is the one deliberate deviation: its classic `typescript` pin (`~6.0.3`) exists only because `svelte-check`'s tooling requires it, while the repository-standard 7.x line arrives through `@typescript/native` and is used explicitly via `svelte-check --tsgo`; see `mail/AGENTS.md`.
- **PHP Version Policy**: `pics` requires PHP `^8.3` in `pics/composer.json` and is developed locally on PHP 8.5. Its PHP extensions must include `pdo_pgsql`, `pdo_sqlite`, `gd`, `intl`, `bcmath`, `exif`, `iconv`, `mbstring`, `openssl`, `tokenizer`, `xml`, `ctype`, `fileinfo`, `curl`, and `zip`. Composer 2.11 or newer is the package manager. Node 24 remains the asset tooling runtime.

## GUI Standards
1. Use a CSS Module (never plain CSS except `globals.css` / `index.css` / `app.css`) imported as `style` in the component file (`.tsx` in the SolidJS and React apps, the `script lang="ts"` block in `mail`'s Svelte files).
2. CSS Modules scope id selectors too. Always bind the module as `style` and reference elements through it (`id={style.navBar}` for a selector `nav#navBar`). Never use a raw unhashed id (`id="navBar"`), and never import a module only for side effects.
3. Selectors are fully nested: `tag#id` (or `tag.class`) with immediate child `>` by default; target descendants only when needed (e.g. `div#app { ... }` and never `#app { ... }`).
4. Never use class for styling; use id. Classes only for style variants.
5. Every time you make a component or a page, its most ancestor / root element must be the semantic HTML container element (`<main>`, `<nav>`, `<header>`, `<footer>`, `<section>`, `<aside>`, `<article>`, `<form>`, etc.) that best represents and describes its content. If none can be chosen out of the semantic HTML container elements, `<div>` may be used.
6. Element ids and classes are camelCase, taken from the component's CSS Module.
7. Never use `<>`/`</>` fragments or SolidJS/React `<Fragment>`.
8. Do not put the title in the logo unless explicitly told.
9. You do not have to run `npm run build` to check if it builds correctly during active development.
10. Global Selectors: Since ids are scoped by modules, `:global(...)` is required for global or router active selectors: `&:global(.active)`.
11. File Mirroring: TSX components and routes mirror their CSS Modules under `src/styles/` (or co-located `page.module.css` where configured).
12. The CSS Module and mirrored-file rules above apply to the JS/TS GUIs. `pics` uses Blade, Livewire, Flux UI, and Tailwind 4 because Blade has no CSS Module pipeline; see `pics/AGENTS.md`. Semantic HTML, keyboard operation, focus visibility, reduced motion, and color contrast still apply there.

## Framework Idiomatic Principles (Complete Compliance Required)
Every application must be written strictly idiomatic to its underlying framework across all layers (components, reactivity, routing, data fetching, mutations, cookies, and server/client boundaries):

### SolidJS Core (`social` and `dvibd/gui`)
- **Fine-Grained Reactivity**: Use `createSignal`, `createMemo`, `createEffect`, `onMount`, `onCleanup`.
- **Never Destructure Props**: Prop destructuring breaks Solid reactivity. Access props directly as `props.propName` or use `splitProps` / `mergeProps`.
- **Control Flow Components**: Use built-in Solid flow primitives: `<Show when={...} fallback={...}>` (never JSX `&&` / `||`), `<For each={...}>` for reactive list rendering (never array `.map()`), `<Index each={...}>` for primitive item lists, and `<Switch>`/`<Match>` for multi-condition branching.
- **Routing & Links**: Use `@solidjs/router` components (`<A>`, `<Navigate>`, `useNavigate`, `useLocation`, `useParams`, `useSearchParams`). `social` uses file-based routes; `dvibd/gui` wires `Router` and `Route` declaratively in `src/uis/index.tsx`.

### SolidStart (`social` only)
`dvibd/gui` is not SolidStart and has no server runtime, so everything in this subsection applies to `social` alone.
- **Data & Mutations**: Use SolidStart `query`, `createAsync`, `cache`, and `action` / `<Form>`.
- **Server Boundaries & Cookies**: Server functions use `"use server"`. Never import server-only packages into client-bundled files. Access request events via `getRequestEvent()` and manage cookies via `h3` (`getCookie`, `setCookie`, `deleteCookie`).
- **Metadata**: Use `@solidjs/meta` (`<Title>`, `<Meta>`).

### Next.js App Router & React 19 (`message`)
- **React Server Components (RSC) by Default**: All components, layouts, and pages under `src/app/` are Server Components by default. Keep data access on the server.
- **Client Components Directive**: Add `"use client"` only at the top of leaf files requiring browser APIs, hooks (`useState`, `useEffect`, `useRef`), or interactive event listeners (`onClick`, `onChange`, `onSubmit`).
- **JSX Conditional Rendering**: Use ternary expressions (`condition ? <El /> : null`) or explicit branch returns. Never use `&&` or `||` in JSX to prevent falsy DOM rendering.
- **Routing & Special Files**: Adhere strictly to App Router conventions (`layout.tsx`, `page.tsx`, `loading.tsx`, `error.tsx`, `not-found.tsx`). Use `next/link` (`<Link>`), `useRouter`, `usePathname`, `useSearchParams`, `redirect()`, and `notFound()` from `next/navigation`.
- **Data Fetching & Streaming**: Async/await data fetching directly in Server Components wrapped with `<Suspense fallback={<Skeleton />}>` for streaming.
- **Mutations & Server Actions**: Use Server Actions (`"use server"`) for mutations, form handling with `useActionState`, `useFormStatus`, `useOptimistic`, and `revalidatePath` / `revalidateTag`.
- **Route Handlers & Cookies**: Route Handlers in `src/app/**/route.ts` exporting standard named HTTP method handlers (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`). Access cookies via `cookies()` from `next/headers` (`await cookies()`) and headers via `headers()`.
- **Middleware**: Use Next.js `src/middleware.ts` with `NextRequest` and `NextResponse`.
- **Metadata**: Export static `metadata: Metadata` or dynamic `generateMetadata()` from `layout.tsx` and `page.tsx`.

### React 19 on Vite (`cv`)
- **Static SPA**: `cv` has no server runtime. All content is build-time data from `src/content/cv.ts`; do not add server functions, route handlers, or runtime fetching.
- **Components and Hooks**: Function components and hooks only, no class components. Keep `StrictMode` in `src/main.tsx`. Clean up subscriptions, observers, timers, and event listeners in effect cleanups.
- **JSX Conditional Rendering**: Use ternaries (`condition ? <El /> : null`) or explicit branch returns. Never use `&&` or `||` in JSX.
- **Routing**: The page is a single scroll with anchor links. Do not add a router unless a second route exists.
- **Content**: `src/content/cv.ts` mirrors the sibling resume repository's `cv.md`. Never invent experience, metrics, dates, titles, certifications, or skills.
- **Styling**: CSS Modules imported as `style`, semantic root elements, and the repository GUI standards apply. The `design-taste-frontend` direction and house rules are advisory; the repository standards win.

### Svelte 5 Core (`mail`)
- **Runes Mode Everywhere**: Components are written with Svelte 5 runes: typed props via `let { ... } = $props(): Props` with an explicit interface, `let x = $state(...)` for reactive state, `$derived(expr)` for computed values, and `$effect(...)` for side effects alongside `onMount`/`onCleanup` from `svelte` when the lifecycle is needed. Destructuring props is idiomatic here (unlike Solid) and stays reactive under runes. Legacy Svelte 4 patterns are not used: no `export let` props, no `$:` reactive statements, and no `createEventDispatcher`. Component-to-parent communication is typed callback props (`onSelect`, `onClose`). Shared reactive state lives in `.svelte.ts` modules using `$state` / `$derived` (classes or plain modules); `svelte/store` (`writable`, `readable`) is reserved for third-party interop.
- **Markup Control Flow**: Use Svelte's control-flow blocks: `{#if}` / `{:else if}` / `{:else}`, keyed `{#each list as item (item.id)}`, and `{#await promise}` with its `{:then}` / `{:catch}` branches (or the `{#await promise then value}` shorthand). Never render elements through `&&` or `||` expressions; the falsy-render hazard exists in Svelte markup too (`{0 && text}` renders the literal `0`). Ternary expressions are fine for text nodes and attribute values.
- **Template Reuse**: `{#snippet}` plus `{@render}` replaces both slots and render-prop patterns; type snippet params with `Snippet` from `"svelte"`. `<slot>` is not used, nor `<svelte:fragment>` shims; composed children arrive as `let { children } = $props()` and are rendered with `{@render children?.()}`.
- **Events & Bindings**: DOM listeners use the lowercase attribute form with direct function references (`onclick={handler}`, `oninput={handler}`), never the legacy `on:` directive form. Two-way values use `bind:value` and friends, with `$bindable` on props that flow back up. The `class:` directive and `svelte/transition` animations remain current and allowed.
- **Stays Local**: These idioms apply to `mail` only. Never apply them to the SolidJS apps; never apply SolidJS, React, or SvelteKit guidance to `mail`.

## API & Endpoint Standards
- Above every endpoint, write the URL preceded with the request verb (e.g. `POST /auth/signup`, `POST /conversations`).
- Keep APIs idiomatic to their respective framework and runtime.

## ORM & DB Standards

### Schema & Clients
- `orm/prisma/schema.prisma` is the single source of truth for the Node applications' database schema. The Node apps are clients of this ORM and do not define their own schema.
- `pics` is the one app outside the Prisma schema. Its Laravel migrations under `pics/database/migrations` own its tables in the separate `dvibd_pics` database. Never add `pics` tables to `orm/prisma/schema.prisma`, and never run Prisma migrations against `dvibd_pics`.
- Keep every generator block intact when editing the schema: `api-client` (outputs to `../../dvibd/api/src/generated`), `gui-client` (outputs to `../../dvibd/gui/src/generated`), `social-client` (outputs to `../../social/src/server/generated`), and `message-client` (outputs to `../../message/src/server/generated`).
- Whenever the schema is modified, regenerate all client packages from `orm/`:
  ```bash
  cd orm && npm run generate
  ```
- After regenerating, verify the client consumers typecheck: `cd dvibd/api && npx tsc --noEmit` and `cd social && npx tsc --noEmit`.

### Migrations
- Migrations live under `orm/prisma/migrations/` and are tracked in git. Prisma's documentation calls this folder "the source of truth for the history of your data model" and requires committing the entire folder, including `migration_lock.toml`, because `prisma migrate deploy` replays only the migration files and never reads `schema.prisma`.
- Migrations are schema history, not a data store. Each generated `migration.sql` holds DDL only (`CREATE`, `ALTER`, constraints); applied state is recorded in the database's `_prisma_migrations` table. A migration may legitimately include a hand-written data backfill, but never a dump of rows. Seeded and demo content does not belong in migrations: local fixtures live in `social/scripts/seedData.mts` and per-signup demo rows come from `social/src/server/demoContent.ts`. Never add an ignore rule for `orm/prisma/migrations/`.
- Create and apply a migration during local development from `orm/`. The script sets `LOCAL_ENV=1`, which locks it to the local `db/` service:
  ```bash
  cd orm && npm run migrate -- --name <migration_name>
  ```
- `migrate dev` is local only. Never run it against anything other than local `db/`.
- Apply pending migrations to a hosted database with `DIRECT_URL` (the Supabase session-pooler URL) or `DATABASE_URL` supplied by the invoking shell, never a `.env` file, and run it before deploying app code:
  ```bash
  cd orm && DIRECT_URL="<Supabase session-pooler URL>" npm run migrate:deploy
  ```
  `DATABASE_URL="<...>" npm run migrate:deploy` is the equivalent form. The script exits non-zero when neither variable is set, so it can never fall through to the local URL.
- `20261106120653_add_post_view_count` is already applied to hosted Supabase by the earlier incident. Do not run it again and do not edit the migration file; a future `migrate:deploy` skips it because `_prisma_migrations` records it. The operational fix for that trap is `orm/config.ts` plus the `migrate:deploy` guard, and `DIRECT_URL`/`DATABASE_URL` should come only from the invoking shell or Netlify env.

### Database Service
- The local Postgres service is managed via `db/docker-compose.yml`. Start, stop, log, and health-check commands live in `db/AGENTS.md`.
- Local data is not backed up anywhere. It lives only in the `dvibd_pg_data` Docker volume and is reproducible from the tracked migrations plus `social`'s `npm run db:seed` followed by `message`'s `npm run db:seed`; `docker compose down -v` deletes it. `db/init/` is empty, so a fresh volume starts with only the base database. The `dvibd_pics` database is created once by hand; see Pics Database below.
- Production data lives in Supabase and follows that project's plan: paid plans get automated daily backups (7 days on Pro, 14 on Team, 30 on Enterprise) with optional Point-in-Time Recovery, while Free projects get no automatic backups and should be dumped periodically with `supabase db dump`.
- Never point OpenCode at a new or scaffolded Prisma project. This repository already owns its schema and clients; work only through the `orm/` scripts above.

### Pics Database
- `pics` uses a separate database, `dvibd_pics`, on the same local Postgres instance (`127.0.0.1:3001`, user `dvibd`, password `dvibd`). It is not part of the Prisma schema and has no generated client.
- Create the database once with `CREATE DATABASE dvibd_pics OWNER dvibd;`. Its schema is then owned entirely by Laravel migrations.
- From `pics/`, apply migrations with `php artisan migrate`. Tests run against SQLite in memory, so they never touch `dvibd_pics`.
- Never run `prisma migrate` or `prisma db push` against `dvibd_pics`.

### Deployment (Netlify)
`pics` is not deployed to Netlify: Netlify has no PHP runtime and no persistent filesystem, so a Laravel app cannot run there as-is. Its deployment target is still undecided; do not add a `netlify.toml` to `pics/`.

Netlify hosts `social` and `message` with their own backends, the `dvibd/gui` SPA, and `dvibd/api` as a functions-only project. Each app is its own Netlify project with its own `netlify.toml` beside its `package.json`, and the site's base directory must be that app directory. There is no root `package.json`, so run Netlify CLI commands from inside an app directory rather than the repository root.

- `message` (project `message-dvibd`) publishes `.next`. Netlify injects its Next.js runtime automatically, so `@netlify/plugin-nextjs` must not be added to `package.json`. Its `src/proxy.ts` runs as an Edge Function in the Deno runtime, so nothing on its import path may reach `db.ts`; see the `jwt.ts`/`tokens.ts` split in `message/AGENTS.md`.
- `social` publishes `dist`, not `dist/client`, because it builds through `nitro/vite`. Nitro detects the Netlify build environment and emits the catch-all function to `.netlify/functions-internal/server/server.mjs`. Do not add `@netlify/vite-plugin` to that app, since that path produces the `dist/client` layout instead.
- `dvibd/gui` publishes `dist` and needs the SPA redirect, because its routing is declarative and client-side. Its `/api/*` redirect proxies to the `dvibd-api` project, so the browser calls the API same-origin and the fetch calls under `/api/auth/` need no production base URL.
- `dvibd/api` (project `dvibd-api`) publishes an empty `public/` directory and runs entirely through `netlify/functions/api.ts`, whose `config.path = "/*"` hands every request to the Hono app. Netlify bundles the function with esbuild, and native `bcrypt` is the only compiled dependency. The build command's own work is `prisma generate` plus creating that empty directory; there is no application build step.
- Every app's build command runs `prisma generate` from `orm/` first, since each generated client directory is gitignored and absent from a fresh clone. `npm --prefix` is what reaches the sibling directory; the prefix differs per app because the base directory differs.
- `NODE_VERSION` is pinned to `24` in each `[build.environment]`, per the Node version policy above. Netlify derives the functions runtime from the build version.
- Production database is Supabase, reached through the **Supavisor session pooler**, never the direct connection string. Netlify functions run in IPv4-only AWS environments, and each warm function instance opens its own `pg` pool against a hard connection cap, so a pooled URL is required. `dvibd/api` caps its adapter pool at one connection per instance (`max: 1`) because the session pooler holds a backend connection for each client it accepts.
- Secrets live only in Netlify's environment, set with `netlify env:set --context production --secret`. Never commit them; `*.env` is gitignored.
- `--secret` values are write-only and reach any build running off Netlify masked (asterisks plus the last four characters), while code running on Netlify reads them unmasked. Every app's `build.command` therefore starts with a guard keyed on those asterisks for local CLI builds, which never fires on Netlify-hosted builds. `social`'s, `dvibd/gui`'s, and `dvibd/api`'s guard unsets both `DATABASE_URL` and `DIRECT_URL`, so a locally inherited masked value cannot reach `resolveDatabaseUrl`, and `prisma generate` falls through to `orm/config.ts`'s local URL, which it can use because it does not connect. `message`'s instead exports a build-only placeholder URL and unsets `DIRECT_URL`, then rewrites `.next/standalone/.env` to the dev defaults after `next build`: its edge-function bundling evaluates the middleware module graph in a process that inherits the CLI environment rather than the build command's shell, and the runtime plugin unconditionally requires that file while a copied-through one would carry the machine's real `DATABASE_URL` into the shipped artifact. The rewrite also removes any need for a local `.env` file. A local `netlify deploy --prod` for `message` must therefore run with placeholder `DATABASE_URL` and `JWT_SECRET` exported in the invoking shell. `JWT_SECRET` is never read at build time, so its mask is harmless. The earliest invocations after a first deploy can run before secret values reach the function runtime; diagnose with `netlify logs --source functions --function <name>` (`server` for `social` and `message`, `api` for `dvibd/api`) rather than assuming misconfiguration.
- **CI/CD is not configured yet.** No app is linked to Git continuous deployment; every project is published by a manual `netlify deploy --prod` from its own directory against a locally built artifact. `social-dvibd` currently reports empty `build_settings` and `commit_ref: null` on its deploys, so its `netlify.toml` build command does not run for those uploads and the local build must already contain the generated Prisma client. Repository-linked CI/CD for all apps is a planned follow-up. Until it lands, verify the deployed artifact and the live routes, not just the build exit code: the Vite 8.2.1 and Rolldown 1.2.3 server-chunking bug produced a build that exited zero while every production route returned 500. The fix is the `vite` pin at `^8.3.5` in `social/package.json`, which resolves Rolldown 1.2.15 or newer.

### Prisma Skills
`skills-lock.json` at the repository root is the tracked source of truth and pins all forty third-party skills. Those forty are gitignored because they are regenerable. One hand-written skill, `sticky-scroll-headers`, is tracked in git instead, so it survives `git clean -xfd` on its own.

Before any Prisma schema, migration, client, or query work, run this from the repository root:

```bash
npx --yes skills@1.5.14 experimental_install
```

Run it unconditionally. It is idempotent and self-healing: it restores every skill from `skills-lock.json` when the directory is absent (fresh clone, clean checkout, `git clean -xfd`), and does nothing harmful when they are already present. Do not pre-check whether the directory exists; do not run `skills add`, `prisma init`, or scaffold a Prisma project to obtain them.

`npx skills experimental_install` restores only the forty lock-pinned skills. The eight Laravel Boost skills are installed by Boost and are not in `skills-lock.json`. After a clean checkout, restore them from `pics/`:

```bash
cd pics
composer install
php artisan boost:install
```

Run `boost:install` interactively and select OpenCode, guidelines, skills, and MCP. It writes `pics/boost.json`, which is gitignored, so a fresh checkout needs `boost:install` again. If you run it non-interactively, verify that `pics/boost.json` contains `"agents": ["opencode"]`; the installer omits that key in non-interactive mode, and `boost:update` refuses to run without it. When `pics/boost.json` already exists, `php artisan boost:update` regenerates the guidelines and skills. `pics/config/boost.php` points Boost's OpenCode skill output at the repository-level `.agents/skills`, so both commands keep them there. See `pics/AGENTS.md` for the generated skill list.

## Workspace Memory

### Env Resolution Policy (implemented)
`LOCAL_ENV=1`, exported by each app's own local scripts (`dev` and `start` in `dvibd/api` and `message`; `dev`, `start`, and `preview` in `social`), marks a localhost test run. The config modules (`dvibd/api/src/config.ts`, `social/src/server/config.ts`, `message/src/server/config.ts`) resolve in this order:
1. `LOCAL_ENV=1` set: return the checked-in dev defaults (`postgresql://dvibd:dvibd@localhost:3001/dvibd` plus the per-app change-me secret), ignoring `process.env` entirely.
2. Otherwise, `process.env`, when the variable is set (Netlify's injected site env in every hosted runtime, and any locally exported value, such as one loaded from a local `.env` by the dev or build tooling).
3. Otherwise, throw.

`dvibd/api`'s `PORT` is the one deliberate exception to step 3: it falls back to `3002` even outside local mode, because the Netlify function never binds a port and only the local server reads it.

`orm/` follows its own resolution policy, owned by `orm/config.ts` and consumed by `orm/prisma.config.ts` through `resolveDatabaseUrl()`:
- `orm/config.ts` owns the local `postgresql://dvibd:dvibd@localhost:3001/dvibd` default.
- `LOCAL_ENV=1`, set by the local `migrate`, `push`, `reset`, and `studio` scripts, locks the run to the local `db/` service and ignores any ambient `DIRECT_URL` or `DATABASE_URL` (warning once per variable when either differs).
- Otherwise it reads `DIRECT_URL` first, then `DATABASE_URL`, from the environment. Every selected URL is validated by zod. There is no `orm/.env` and no dotenv dependency.
- `generate` with no environment falls back to the local URL, because `prisma generate` does not connect.
- `migrate:deploy` requires `DIRECT_URL` or `DATABASE_URL` and refuses to run otherwise, so it can never fall through to the local URL.

**Why the marker wins over `process.env`.** Once the runtimes moved onto Netlify's injected site env, every ambient local variable became a capture risk for a localhost run: a leftover export, or `netlify dev` injecting the site's variables into its dev command, would point local testing at Supabase with the real secrets. The marker makes "testing locally" explicit and deterministic: hosted runtimes never see it because they are not started through npm scripts (Netlify executes the build output directly), while `netlify dev` inherits it because it runs the same dev script.

**Consequence for builds.** `next build` evaluates route handler modules, and build scripts deliberately carry no `LOCAL_ENV`, so a local production build with no `.env` and no exported variables still fails during page-data collection. That is intended: on Netlify the variables are present at build time. To build locally, provide a `.env` file.

Either root implies `--headless`, so the configured server is an in-process engine with the CPU renderer, no window. A bare `mcp` first tries `127.0.0.1:7979` and then falls back to headless; an omitted root grants no access in that direction.
- **Installation.** The CLI is `/home/sadanddan/.local/bin/vectorcraft-cli`, version 0.21.0, matching the installed desktop app `/home/sadanddan/Applications/vectorcraft-0.21.0-linux-x86_64.AppImage`. Vendor release packages ship the CLI beside the app (deb/rpm at `/usr/bin/vectorcraft-cli`, macOS as a separate zip, Windows in the MSI), and source checkouts use `cargo install --path apps/vectorcraft-cli --locked`. The vendor docs are `docs/mcp.md` and `docs/control-protocol.md` in `storytold/vectorcraft`.
- **Attached mode.** Start the app with `--control 7979` (and its own automation roots), then run `vectorcraft-cli mcp` without root flags, or `--connect 127.0.0.1:7979` to fail fast instead of falling back to headless. The port probe happens once at server start, so an MCP server started before the app stays headless until it is restarted.
- **Capabilities.** The MCP surface has 33 tools, 3 resources, and 5 prompts. Command and document work: `command_list`, `command_run`, `command_batch` (aliases `list_commands`, `run_command`, `inspect_document`), `doc_inspect`, `render_preview`, `open_file`, `save_file`, `export`, `undo`, `redo`. Drawing and editing: `draw_path`, `draw_shape`, `set_paint`, `add_text`, `apply_effect`, `pathfinder`, `transform`, `create_graph`, `text_wrap`. UI tools that require the attached app: `ui_inspect`/`inspect_ui`, `ui_screenshot`/`screenshot`, `select_tool`, `pointer_gesture`, `press_key`, `type_text`, `answer_dialog`, `invoke_menu`, `open_panel`. Resources: `vectorcraft://document`, `vectorcraft://document/json`, `vectorcraft://commands`. Prompts: `poster`, `icon-set`, `recolor`, `trace-and-style`, `export-set`. The headless `run` and `convert` batch modes are CLI-only, and `.ait` templates are written by `file.saveAsTemplate` or a `.ait` output path. Start with inspection, describe intended changes, and get approval before writes.
- **Role.** The `graphic-designer` subagent owns VectorCraft vector work; other roles hand vector edits to it.
- **Status.** VectorCraft is free and open source under Apache-2.0. The `reviewer` and `reviewer-go` agents deny `vectorcraft_*`.
